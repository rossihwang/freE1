# 原厂 App 与 freE1 录音质量对比（2026-11-10）

同一台设备、同一扬声器、同一音量（`Master 70%`）、同一段循环测试音，分别用原厂 App
和 freE1 录一遍，做同口径分析。**测法、指标定义与复现步骤见 [NR_TESTING.md](NR_TESTING.md)。**

测试音（30 s 循环）：**5 s 静音 → 10 s 语音状噪声（4 Hz 幅度调制的近粉噪）→ 5 s 静音
→ 10 s 100 Hz→8 kHz 扫频**。原厂录了 195 s（6.5 轮），freE1 录 46 s。

- 原厂产物：`/mnt/sdcard/tempUser/<YYYY.MM>/<ts>_meeting.wav` 与 `..._meeting_denoise.mp3`
- freE1 产物：`/mnt/sdcard/freE1/REC_<seq>_<ts>.wav`
- 分析时统一解码为 48 kHz 单声道，电平比较用 dBFS

## 1. 产物格式

| | 原厂 `meeting.wav` | 原厂 `_denoise.mp3` | freE1 |
|---|---|---|---|
| 采样率 | **16 kHz** | 16 kHz | **48 kHz** |
| 位深 | 16 bit | —（MP3） | **24 bit** |
| 声道 | **1（单声道）** | 1 | **2（立体声）** |
| 编码 | PCM | MPEG-2 Layer III 160 kbps | PCM |

原厂的“原始 WAV”本身就是 **16 kHz / 16-bit / 单声道**：阵列以 32 kHz 采进来，
前端直接降到 16 kHz 输出，不存在高采样率的母版。

## 2. 电平与底噪

| 指标 | 原厂 | freE1 | 差异 |
|---|---|---|---|
| RMS | **−19.7 dBFS** | −31.7 dBFS | 原厂响 12 dB |
| 峰值 | **−1.1 dBFS** | −15.5 dBFS | 原厂几乎贴顶 |
| 静音底噪（帧 p10） | −53.7 dBFS | −56.9 dBFS | 原厂高 3.2 dB |
| 有声段（帧 p95） | −9.7 dBFS | −22.4 dBFS | 原厂高 12.7 dB |
| 有声 − 底噪 | **44.0 dB** | 34.5 dB | 原厂高 9.5 dB |

**这 9.5 dB 不是靠“放大”来的**：原厂整体增益比 freE1 高 12.7 dB，如果只是线性放大，
它的底噪应该落在 −44.2 dBFS，实测是 −53.7 dBFS——也就是说前端额外压掉了约 **9.5 dB** 噪声。
这批录音里降噪档位是 **1（无额外降噪）**，所以这 9.5 dB 来自常开的
**MVDR + MCLP + 去混响 + AGC** 前端，不是 NNSE。

## 3. 频响（LTAS，以 500–1000 Hz 为 0 dB）

| 频率 | 原厂 | freE1 |
|---|---|---|
| 131 Hz | −16.5 | −14.9 |
| 296 Hz | −16.2 | −12.4 |
| 508 Hz | −6.5 | −4.8 |
| 873 Hz | +4.7 | +2.5 |
| **1145 Hz** | **+5.3** | +1.4 |
| **1501 Hz** | **+3.9** | −1.6 |
| 2581 Hz | +4.5 | +1.5 |
| **3384 Hz** | **+5.3** | +2.2 |
| 5817 Hz | −2.0 | +0.4 |
| **7627 Hz** | **−42.9** | −2.8 |

读法：

- 原厂在 **0.9–4.5 kHz** 有 +3…+7 dB 的“存在感”提升（语音可懂度频段）
- 原厂在 **7.5 kHz 以上直接消失**（16 kHz 采样率的奈奎斯特墙）
- freE1 频响平直、延伸到 8 kHz 以上（受测试音限制只到 8 kHz）
- 低频两边都不强，但 freE1 的 300 Hz 附近比原厂高 4 dB（环境隆隆声更容易被收进来）

## 4. 原厂实际怎么采（这次抓到的）

录音瞬间 `/proc/asound/*/hw_params`：

| 设备 | 通道 | 采样率 | 格式 | period / buffer |
|---|---|---|---|---|
| `card0`（codec） | 2 | 32 kHz | S32_LE | 2400 / 14400（75 / 450 ms） |
| `card2`（PDM 阵列） | **8** | 32 kHz | S32_LE | 2400 / 14400 |

两个设备**同时**以 MMAP 打开（合计 10 通道，对应 `/etc/asound.conf` 里的
`multi_10c32k`），App 进程 CPU 占用 **134%**。

降噪档位=1 时，`_denoise.mp3` 与 `meeting.wav` 的粗指标完全一致（都是 16 kHz、同一电平、
同一底噪）——说明这个档位下 MP3 只是同一条 16 kHz 流的再编码，10.5 MB 的 NNSE 模型没参与。

## 5. freE1 的立体声质量

OMNI 模式下 L/R 是同一批声源的两组麦，实测逐带相关：

| 频带 | 相关系数 |
|---|---|
| 80–300 Hz | 0.98 |
| 300–1000 Hz | 0.96 |
| 1000–3000 Hz | 0.89 |
| 3000–8000 Hz | 0.70 |
| 8000–16000 Hz | 0.45 |

单声道下混相对单通道的响应：

| 频带 | 变化 |
|---|---|
| 300 Hz–10 kHz | **+1.0 … +1.5 dB**（相干相加） |
| 10–16 kHz | +0.2 dB |
| 16–22 kHz | −3.5 dB，凹陷在 11.5 / 12.1 / 19.8 kHz（−17…−21 dB） |

结论：**语音带内下混是安全的**（还有 1 dB 增益），梳状凹陷只出现在 11 kHz 以上，
对语音几乎无影响；但作为“立体声”听感，高频去相关是阵列间距带来的，需要时延对齐才能改善。

## 6. 结论：两类不同的产品

| | 原厂 | freE1 |
|---|---|---|
| 定位 | 语音转写笔 | 录音笔 |
| 产物 | 16 kHz 单声道、响、做了语音 EQ 和阵列降噪 | 48 kHz/24-bit 立体声、平直、保守电平 |
| 强项 | 人声清楚、响度大、底噪低约 9.5 dB | 带宽 3 倍、位深多 8 bit、无压缩痕迹、可后期 |
| 弱项 | 7.5 kHz 以上没有、单声道、峰值贴顶容易破 | 没有降噪/波束、电平偏小、低频隆隆声多 |

“原厂声音更好”这个直觉，主要来自**响度 + 语音频段提升 + 噪声抑制**，而不是分辨率——
它的信息量其实比 freE1 少一个数量级（16k/16/mono vs 48k/24/stereo）。

## 7. 优化方向

### P0（1–2 天）

1. **语音预设（Speech preset）**：可选 HPF 100–150 Hz + 1–4 kHz +3 dB 存在感提升 +
   目标电平从 −24 提到 −18 dBFS（“响亮”档），峰值上限仍 −1.5 dBFS。
   这一条能补掉主观差距的一大半。
2. **轻量谱降噪**：20 ms 帧、Wiener/谱减 + 噪声底平滑，目标 6–8 dB。
   不需要 NN，CPU 预算参考：原厂整条链 134%，我们加一个 FFT 域降噪大约 15–25%。
3. **look-ahead 限幅器**（backlog 已有）：把“响亮档”的电平提上去而不破音。

### P1（3–5 天）

4. **全向阵列时延对齐 + 每麦增益**：先修 8 kHz 以上的相位问题，再考虑自适应波束
   （原厂的 CGMM-MVDR 是闭源的，但几何和思路可借鉴）。
5. **单声道选项**：语音场景提供 mono 输出（实测下混安全），也便于转写与对比。
6. **16 kHz 单声道导出**：给转写/分享导一份与原厂同规格的小文件，母版仍是 48k/24。

### P2（需要另立项目）

7. **神经网络降噪**：不能复用原厂模型（闭源 + 自定义二进制），需自训小模型
   （GTCRN / DeepFilterNet 量级，几百 KB～2 MB），用设备实测数据做训练/验证集。

## 8. 二级 / 三级降噪实测（2026-11-10 晚）

把 `recordparam.NoiseReduceMethod` 改成 2、3（改库 + 重启 App），用同一段测试音各录一遍。

### 二级（AFE 固定波束，`config-level2.ini`）

有效数据 72.4 s，16 kHz/16-bit/单声道，与一级同口径：

| 指标 | 一级 | 二级 |
|---|---|---|
| RMS | −19.7 dBFS | −19.6 dBFS |
| 峰值 | −1.1 dBFS | **−0.2 dBFS** |
| 静音底噪 | **−53.7 dBFS** | −46.6 dBFS |
| 有声段 | −9.7 dBFS | −10.9 dBFS |
| 有声 − 底噪 | **44.0 dB** | 35.6 dB |

逐带 SNR：二级在 **每一个频带都低 3–6 dB**（80–200 Hz 21.6→13.2，1–2 kHz 51.1→45.4）。

**但这个对比对二级不公平**：固定波束朝前，而测试音是从设备**自己的扬声器**（朝下/朝后）出来的，
被波束压掉约 2 dB，同时波束的固定指向把底噪抬了上来。要公平评估需要正前方 0.5–1 m 的声源。

### 三级（NNSE）：跑不起来

改到 3 之后原厂 App **启动即崩溃**，`init` 每 1.6 s 重新拉起一次（`e1.log` 里连续多个 PID
都在 `noisereducelevel: 3` 初始化后立刻结束），约 5 分钟后整机被看门狗重启。恢复过程见下。

**手动复现拿到了确定的退出原因**（把档位设成 3，绕开 init 直接运行原厂 App）：

```
last log: [E1.RecordConfig] read current record mode: 1
Segmentation fault
EXIT=139
```

即 **SIGSEGV（信号 11）**，死在录音引擎初始化的最后一步，没有任何错误输出。

根因：**这台设备的固件里没有 NNSE 资产**——`/etc/sogou/front-config/nnse/` 不存在
（只有 `agc/`、`model-1/`、`model-2/`），`find / -iname "*nnse*"` 只剩三个 `.so`，
10.5 MB 的 `nnse.conf.model.bin` 只存在于旧版备份里。SDK 的加载函数是
`load_nnse_conf` / `load nnse conf fail`，App 没检查失败返回值就继续用，解引用空指针 → 段错误。

为什么表现为“不停重启”：`inittab` 里是 `::respawn:/usr/bin/SogouLunchProbe.sh`，
App 一崩就被 init 拉起（实测每 1.6 s 一个新 PID），持续几分钟后整机被看门狗重启；
期间 WiFi 归 App 管，一直起不来，所以 SSH 不可达（USB adb 不受影响，靠它恢复）。

结论：**三级降噪在这个固件版本上不可用**，不是参数问题，是资产缺失。

### 恢复记录

- 崩溃循环期间设备网络不可达（WiFi 起不来）
- 用 USB 上的 adb 通道（`2207:0011` 复合设备带 ADB 接口）把 freE1 的启动槽位写回去，
  杀掉原厂 App，设备恢复；`E1-Cf.db` 的 `NoiseReduceMethod` 已改回 1
- 之后 freE1 正常运行，uptime 持续增长，SSH 恢复

## 9. 还没测的

- 如果拿到 NNSE 模型目录，三级是否可用（值得在备份/旧固件里找）
